# Imported file lifecycle clocks

14 days of inactivity is measured from the original source's last body access for imported versions. The controlled source snapshot records files.last_access_at and files.created_at from the stopped legacy ledger, with a per-row hash and observation time. These facts are stored in mem.storage_source_clocks, separate from mutable file annotations and actual member use events. Copy/ingest/verification does not create use events or reset the clock.

The planner takes the later of original source usage, actual post-migration body_read/adopted/reused activity and the most recent genuine return to Standard. When the source has no last-use fact, original source creation is the fallback. A recognized imported version with neither source fact stays pending; the import date is never substituted. Native new versions retain their existing creation fallback. Pins, authorization, fixed identities, idempotency and physical-retirement guards continue to apply.

20261019-original-source-lifecycle-clock.sql is maintained by the registered Mem database owner. Its source-clock backfill is applied in bounded chunks through the engineering executor. operations/regional-original-clock-import.sql updates the existing postgres-owned, postgres-session-only operational importer; it is applied by the explicitly authorized SSH database operator, preserving the existing owner, ACL and source/current identity checks. Project database-role access does not grant authority to replace that importer. No public source-clock write route is added.

Source last access is preserved as evidence, not reclassified as a new native body read. Unknown source use remains unknown. Fixed source files, versions and originals are retained.

The final dispatch guard uses the same original-source clock as planning. Regression coverage compares both decisions on actual imported Standard versions. Retirement checks use exact indexed provider/bucket/key/version tuples for shared physical locations. UUID-only reference contracts cannot emit physical locator references; JSON-bearing contracts still call the original gc_fact_keys gate, with a conservative ASCII-key prefilter and a full scan fallback for escaped/non-ASCII/complex keys. Read leases, current Source authorization, archive proof and recovery-protection checks are unchanged. Eleven SQL prefilter fixtures cover ASCII, Unicode, escaped and primitive keys.

Reference-field projections are enabled only for the known gc_fact_keys definition fingerprint; a parser change restores the original full reference scans automatically. The source-clock table is registered as GC ledger metadata. The Hufu readable-client predicate evaluates eligible witnesses lazily in the same client-ID order and still checks the original resource_deadline; real permitted/denied scopes and invalid inputs match the prior predicate.

For registered historical versions missing from the private reader admission set, operations/admit-registered-legacy-sources.py accepts a pinned current-authorized candidate manifest, verifies exact cloud VersionId and size, and appends exact locators atomically under the existing local lock. Existing entries and their fixed versions remain intact. Source SHA verification before COPY and current member/Source authorization are still mandatory. This root operational tool does not create a bucket-prefix capability or a member-facing admission API.
