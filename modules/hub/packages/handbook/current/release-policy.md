# 企业 AI 协作平台 · 系统版本和说明书发布机制

适用系统版本：2.10.0 · 文档修订：2026-10-21

统一软件版本
采用主版本.次版本.修订号。兼容修复递增修订号；兼容新增能力递增次版本并归零修订号；不兼容公开接口或行为变化递增主版本，说明迁移路径。组件可保留自身构建标识，不要求每次同步改动全部组件。规划文稿修订号不作为软件版本。

发布与说明书一并更新
1. 核对实际已部署的改动、受影响功能与兼容性，选择下一个版本。
2. 更新本次发布说明和受影响说明书。用现有资料存储服务保存形成真实固定引用；未变更章节复用原固定版本。
3. 通过主管发布接口一次提交系统版本、变更摘要与完整说明书清单及正文。系统校验固定引用对应的正文哈希、当前版本与新版本，保存不可覆盖的版本目录和说明书快照，再原子切换当前版本清单。
4. 网页和MCP从同一当前清单读取。不能只改一个显示数字、只更新策划稿，或在改动未实际部署时声称已发布。

当前正式接口
GET /v2/releases/help：当前契约。
GET /v2/releases/current：线上登记的当前生效版本。
GET /v2/releases：历史版本。
历史正文优先POST /v2/manuals/read，传id和version；GET /v2/releases读取发布历史。路径是否被当前hub2_api包装器开放以实际契约为准。
POST /v2/releases/publish：真实主管及具有管理能力的当前凭据，在实际全局管理范围内发布。
发布body：version、expected_current_version、summary、changes、documentation.documents、idempotency_key。每份文档包括id、title、filename、text、fixed_ref及原有必要元数据；fixed_ref由现有文件保存能力生成。
首次基线expected_current_version为null；后续必须是当前线上版本。每次带适用新版本的release-notes、总纲和本机制说明，未变更的说明书无需制造新的文件版本。
相同主体、相同发布标识和相同输入可恢复同一成功结果；已发布版本不得覆盖，新改动必须增加版本。并发与版本冲突返回真实错误，不覆盖别人的发布。发生未完成的文件快照时保留供主管按原标识核对恢复，不能盲目重发。

历史与纠正
POST /v2/manuals/read支持id和可选version。传入version读取当时冻结的正文与固定引用，不自动换成最新正文。固定历史引用继续有效。
当前没有在线回退接口；需要回退时通过工程恢复和新的明确发布记录处理，保留原版本历史。不能静默删改历史或把未发布草稿当线上状态。
纯文案修订不等于软件功能升级；系统发布仍必须提交与新版本对应的说明书清单。需要单独修正文档时应记录适用的软件版本和文档修订，不改写已经冻结的历史快照。

成员发现更新
网页显示版本与变更摘要；展开详情标记本浏览器已查看。本人资源提示只由当前成员可领取清单产生。MCP的hufu_context和hub2_context返回当前版本、变更说明和本人资源提示。
“已授权”“已展示”“已查看”“已下载”含义不同。通知只提供操作入口，实际领取仍走本人权限和邮箱验证。未查看提示不能阻止操作，普通程序不必调用上下文、读取通知或提交Agent留痕才能运行。

## 跨项目补录检查

有功能更新时同时核对正式历史、当前工具目录、所属工程提交/实际部署、成员工作阶段与协作交接，不能只凭release列表或最新工作摘要宣称查全。记录每项已部署、源码候选、资源交付、待验收及不适用的依据；组件版本和产品版本分别列出。
对已经上线却漏登记的能力，发布新的系统版本并同步受影响手册，保留原发布2.9.0等冻结正文；不倒填旧发布日期。只因改名、README或单机检查通过，不将未部署功能登记为当前可用。核查报告列明截止观察时间、权限及来源覆盖，后续变化继续按新证据更新。
本次2.10.0补齐此前已上线兼容能力与修复登记，没有为文档补录重启所有服务，也没有宣称统一工作流程策划和AutoDL队列已落地。

历史版本与变更记录保存在正式发布档案；通过 POST /v2/manuals/read 提供本篇 id 和指定 version 可读取对应冻结正文。
