# 身份权限服务 · 全项目授权与资源接入

适用系统版本：2.8.0 · 文档修订：2026-10-18

项目工作资格、工程资格、数据库对象、资源目标和文件交付是不同通道。已有资格直接工作，缺失范围申请；主管在真实管理范围可主动授权。权限终止使用撤权；新需求重新申请，不冻结或解冻。

通过 GET /v2/authorization/help 读取真实工作流，再用 hufu.access.catalog/prepare 定位项目和目标，apply 提交，applications/decide 处理，permissions/overview 回读，change 撤权。工程专门入口见 project-engineering；个人应用记录按其独立授权规则使用。项目隐私读取使用下述双角色通路。

普通成员接入后可在本人范围创建个人项目、保存资料和建立工作；同一成员不同有效MCP共享已批准项目资格，无需每项工作或每个客户端再申请。服务主体保留独立动作边界；真正专项资源和外部供应商条件仍以当前权限校验。项目和工程沿同一project_id，不另建同名宏观项目。

资源必须绑定登记的真实对象、账号、产品、消费者和期限。嘉兴与JIE是不同来源账号；Lighthouse与CVM不能混用，IMDS实例号不能推定对应CVM控制目标。托管执行不要求把云父密钥交给成员；项目资格不产生整机或跨项目权限。

文件交付用delivery通道，批准必须绑定真实item_id，流程见vault-delivery；只授予文件领取，不产生服务器或项目资格。停止领取不能召回已发出值，外部密钥撤销需实际来源生效。

授权、审批、供应商调用、部署和业务使用分别回读，状态不明查询原operation。历史案例、来源纠正与账号核验保留在原固定版本；本版按任务提供当前使用规则，具体资源资格、期限和可用性按当前发现返回。

## 项目分类与默认读取

项目分类为 team（团队）、personal（个人）、private（隐私）。团队和个人项目默认对当前组织的成员可读；项目写入仍检查本人的工作资格。个人表示项目归属，不表示保密。现有个人项目沿同一编号执行新的默认读取规则，资料和工作历史保留。

新项目默认个人。团队项目只能由实际主管创建；主管也可将公开的个人项目提升为团队，保留原成员归属和原编号。创建时不能直接选择隐私；创建后项目本人通过 v8.project.convert 显式标记 private。如需取消隐私，也由项目本人显式操作。主管身份和旧工作资格均不能绕过隐私读取或替本人取消隐私。

## 隐私项目双角色授权

本人保留自己的项目工作能力。其他成员或指定软件读取隐私项目，必须在同一申请中取得实际项目本人和实际组织主管两方授权。授权只提供读取门槛，写入和工程等动作继续检查其专项资格。

通过 hub.tools 查询 hufu.project.privacy.* 当前契约：

- apply：读取者用已知 project_id 申请本人读取；项目本人也可用 grantee_id 邀请指定成员或服务主体。未授权时项目不能按名称被发现，引用需来自本人提供的实际项目链接。
- requests：按 mine、owner、supervisor、all_visible 和原 request_id 查询。申请队列提供授权所需元信息，不包含隐私项目内容。
- decide：按请求当前 revision 提交 expected_revision；approve/reject 明确 leg=owner 或 supervisor。签署者由实际登录/MCP身份导出，不接受正文中的操作者或批准者。本人和主管是同一真实主体时，允许其分别显式签署两个角色，不代签其他成员。
- revoke：项目本人或主管按 CAS 撤销申请授权。之后重新读取须重新得到两方授权，旧资格不补足缺失的任一方。

变更操作保留 idempotency_key，响应不明时先查原申请。可指定 expires_at，或 until_revoked=true（默认）；任一批准者失去相应身份/资格、授权到期或项目范围改变时，旧授权失效。隐私读取的源角色、项目和授权记录共同参与最终权限检查。

公开API合同：GET /v2/projects/privacy/help；POST /v2/projects/privacy/apply、requests、decide、revoke。统一沿当前成员身份，服务器管理与供应商凭据不因默认项目可见而自动交付。

历史版本与变更记录保存在正式发布档案；通过 POST /v2/manuals/read 提供本篇 id 和指定 version 可读取对应冻结正文。
