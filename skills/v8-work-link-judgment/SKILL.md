# 工作颗粒度、生命周期与采用关系

依据当前用户目标和真实工作内容判断。按需读取官方 `/v2/work-items/judgment-policy`；规则由V8维护，本Skill提供执行方法，不增加权限或写入必填门槛。

## 先确定初始任务颗粒度

一个任务对应一个具体用户行为闭环的一次明确交付：在什么情况下，用户做什么，最终得到什么结果。建立时说明本次覆盖范围和可判断完成的证据；研究、写作等任务用具体交付结果及其使用目的表达闭环，不强行虚构软件操作。

- 同一闭环涉及的接口、模块、平台适配、重试、测试和发布，默认是内部步骤，不按文件、工期、代码量或参与者数量拆号。
- 出现新的用户用途，或者同一闭环新增一项值得单独安排、交付和验收的明确能力或效果，可以新建任务。不能仅因用户最终目的相同就无限沿用。
- “全面优化产品”过宽；“调整一个按钮”通常过细。若干小优化按同一用户场景、同一次明确交付合并，不建一个无限收集零碎问题的优化任务。
- 尚无具体预期效果的“还能更好”先保留为优化候选，不立即建立进行中任务。资料保存和普通讨论可作为已有任务的过程记录，不自动造号。

## 判断沿用还是新建

用一句话说明本次具体结果和完成条件。读取最可能的已有工作，比较其**原目标**、最新进展和本次结果；不要只与最近一条阶段摘要比较，也不因同产品就沿旧号。候选仅为线索，实际使用哪个工作须读取其内容。

- 为达到本次约定结果所需的研究、实现、普通修复、测试、发布或交接，沿用原号；已交付后的新增优化和维护按下述生命周期判断。
- 新增结果可独立交付/验收，且不是原结果的必要步骤，新建编号；新工作也可直接引用旧成果。
- 为沿用旧号而不断扩写原目标时，重新判断边界；反过来，不按日期、对话、文件、提交或一次重试碎拆。
- 只有新增交付、实质方向变化或发现错归属才重判；普通步骤无需重复填表。

## 再独立判断是否关联

新建/沿用都不自动决定关系。问清：**用了哪项具体结论、实现、待办或纠正，影响本次哪一步？**

- 能指出实际直接采用、承接待办、回应或修正的来源，记录简短依据，采用有权读取的原工作与固定版本。
- 只同项目、同主题、共用基础组件，或只查看过而未实际采用，不据此建边。
- 理由已写“实际复用/直接承接”，却准备提交空关联时，核清来源是否对应某项工作；确认则登记，尚未核清则标待补。不要把“比较过的工作”全部关联。
- 候选缺失、默认布尔值、阶段unassessed和追溯失败都不是关系不存在的证明；程序读取问题与AI判断分开处理。

需要相近经验时只读 [判断案例](references/decision-cases.md) 中对应场景。案例是上下文对照，不是按词匹配的判定表。

## 判断状态、结束与后续维护

编号回答是否同一项工作，状态回答是否结束，关联回答实际采用了谁；三者分开判断。当前V8状态为open、in_progress、completed、cancelled，使用实时契约，不自行增加状态值。

- 目标已确定但尚未开始为open；实际推进后为in_progress。等待权限或外部条件时在进展中写明卡点与恢复条件，不为等待另建编号或虚报完成。
- 达到本次约定范围和完成条件，并有相称证据，才标completed。行为交付不能仅凭按钮存在、代码或构建成功；仅源码交付的任务也不强加未约定的生产部署。无需证明整个产品再无缺陷。
- Agent按约定条件和证据判断完成，不默认每项都等用户确认。明确要求用户验收而尚未验收时，分别记录“开发完成”和“用户验收待完成”；若该验收属于本任务完成条件，整体仍为in_progress，不能混称全部完成。不得为结束任务自行降低或删去原完成条件。
- 明确决定不再实施才标cancelled，保留原因和已有成果；暂停、等待或一时受阻不等于取消。一次就完成的任务可直接登记completed，不强制走一遍中间状态。
- 刚交付即发现原承诺未达到，通常纠正完成判断并继续原编号，保留此前完成声明和纠正依据。交付使用后发现、需要独立安排的维护修复，可以新建关联的修复任务，保留旧交付事实并追加说明，不能掩盖旧缺陷。时间长短不是自动拆号或重开依据，仍看原承诺与当前修复交付的边界。
- 原闭环已完成，后续新增能力或明确性能/体验提升，可新建优化任务，旧任务保持完成。用本次新增效果和验收条件说明边界，不只凭“大优化/小优化”标签；实际采用旧实现或成果时另记关联。
- 完成条件固定于当时约定的交付，不因后来提出优化而无限上调。已完成工作仍可被读取和引用，结束不删除其成果、来源或关联。

## 写入与核对

按实时 `hub.help` 契约调用 `v8.work.save`：在 `properties.work_judgment` 中表达决定、简短理由与实际读过的候选；关联另用 `related` 和具体 `basis.explanation`，可带真实读取回执/固定依据。新编号由平台生成，不自编；修改已有主状态按实际revision/CAS。失败重试保留原幂等键，先核对原结果，不重复造号。

只核对本轮实际提交的决定：理由说实际采用但关联为空时核清来源或标待补；保存后核对返回编号、所改状态和提交关联是否正确读回。遗漏检查关注理由与登记一致，读回关注系统实际保存，两者均不证明语义判断一定正确。已有错归属保留原编号与历史，追加纠正；必要时新建并引用真实旧成果，不批量搬迁、自动补边或虚报旧工作完成。普通步骤不重复整套判断，只在建立、实质范围变化、结束或纠正时检查相关部分。

## 迭代

后续真实任务保留“任务输入→候选原目标→选择理由→采用关系→实际纠正”的必要证据。实际结果支持时才修订案例，保留反例与适用条件；不把数据增多当成模型自动训练或准确率提升。通用方法可共享，个人原文仍留在原授权范围。
