# 设计原则

## 当前任务和真实代码优先

开始时读取当前任务、项目规则和直接相关代码。当前用户最新决定优先于旧策划，当前项目规则优先于历史任务书，实际 Contract 和运行行为优先于过期说明。

评审或诊断保持只读；实现请求在明确范围内推进。只有产品方向、公共架构、Host 边界、账号权限、生产数据或网络可达性发生实质变化时才请求额外裁定。

## 复杂度必须有理由

- 小问题使用局部、可读、可回归的修复。
- 只有多个调用者需要稳定语义时才抽公共 Contract。
- 只有外部服务或平台细节需要替换、隔离或测试时才引入 Port／Adapter。
- 只有真实并发、恢复、计费或审计需求存在时才建设对应状态机。
- 不为表现“工程化”而增加层级、任务书、证据包或重复文档。

## 稳定能力与接线分开

可复用领域语义和算法放在稳定层；当前产品的 UI、数据库对象、页面流程和 Host 接线留在产品层；模型、云服务和系统工具通过明确 Adapter 接入。供应商字段和临时路径不能成为公共 Contract。

对于单产品、低复杂度功能，可以保持更简单的结构。能清楚测试和替换边界，比目录名称是否齐全更重要。

## 硬事实与认知判断分开

类型、格式、范围、大小、摘要、预算和状态转换通常由确定性代码处理。语义匹配、意图和内容质量可以由模型或 Agent 处理，但应通过现有 Contract 表达置信度、理由或澄清需求。

## 状态声明必须可验证

区分源码实现、本地测试、构建产物、部署、真实端到端和正式验收。任何一层的成功都不能自动外推到下一层。
