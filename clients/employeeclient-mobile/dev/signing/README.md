# 本机稳定签名

目的：让同一员工客户端连接器的后续版本具有相同的签名身份，以验证并减少钥匙串重复授权。不是 Apple Developer ID、不是公证，也不承诺绕过首次运行检查或所有系统权限提示。

- `setup-local-identity.py` 只运行一次。私钥和临时 PKCS#12 始终在内存中传给系统钥匙串，不写私钥文件。公开证书位于本机 Application Support/EmployeeClientConnector/signing。已有证书存在时复用；构建不调用生成脚本。
- `connector-mac/signing.py` 保存的是公开证书指纹，构建 spec 与更新验证复用它。更换身份必须另做迁移，不能每次构建自动生成新证书。源码包不包含私钥；另一台构建机需要通过用户批准的安全方式迁移签名身份。
- 第一次 `codesign` 使用钥匙可能要求 macOS 确认。这是构建钥匙的授权，不是每个版本的手机配对或连接器运行授权。
- `verify-keychain-continuity.py` 编译两个代码不同的原生程序，分别用同一证书签名。第一版在独立临时钥匙串写入假数据，第二版禁止系统交互后读取；另一身份必须不能读取。测试只删除自己创建的临时钥匙串，不接触员工客户端真实配对。
- 通过上项之后，还需用完整 PyInstaller 应用验证安装、启动和真实配对保留。旧 ad-hoc 迁移到新证书的一次授权不能算后续升级失败；第二个同证书构建再次要求授权则必须继续诊断。

自签名只用于当前用户同意的内部/个人分发路线，不自动修改系统信任、TCC、Gatekeeper 或钥匙串 ACL，不开放“允许所有应用”。公开商业分发仍应考虑 Apple Developer ID 与公证。

2026-09-24 验证：两个不同二进制使用同一证书，第二版在禁用系统交互时成功读取测试凭据；换成 ad-hoc 后返回授权拒绝 -25293。完整 PyInstaller 应用自检通过。PyInstaller 会自动启用 hardened runtime；因本机证书没有 Apple Team ID，只给本应用添加 disable-library-validation 以加载包内 Python，未添加 JIT、未签名执行内存等其他豁免。更新仍须通过全包完整性和精确证书校验。参考：https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation

外部安装定位可以识别既有 <=57 的旧签名应用以原位覆盖；任何传入更新包仍须匹配固定证书，不允许借迁移入口装入其他签名。

## 系统登录钥匙串的实测纠正（0.49.9.1）

独立临时钥匙串的同证书 DR 测试通过，不足以证明系统登录钥匙串的跨版本授权。真实配对的只读 ACL 检查发现其 partition 包含各版 cdhash；更换实际完整应用后再次触发了授权。因此“固定本机证书即可消除重复提示”的推论撤回。

最终方案：将 Keychain 的拥有者独立为 `Contents/Helpers/EmployeeClientKeychain`。它不含版本/UI/业务代码；当前二进制及公开摘要清单随源码交付，后续构建逐字节复制，不能自动重编译或重新签名。源码改变或摘要不符直接阻断构建，组件升级须另做迁移。证书仍固定，用于组件与主程序的双向身份校验。

组件先校验真实父进程的签名标识与证书，只接受员工客户端主程序；再处理固定配对条目的读取/写入/删除，及限定格式的无敏感 self-test 条目。普通 shell/Python 直接调用会以 77 拒绝，凭据不进入 argv、文件或日志，只通过父子进程管道传递。没有改系统分区 ACL、没有开放所有应用。

旧配对首次交由稳定组件读取仍需系统允许。是否真正不再重复提示，以两个主应用构建在相同安装路径替换后都恢复 online 为准；不能再用临时钥匙串或构建通过代替。

最终实包验证已通过：用户完成稳定组件首次迁移后，两个代码摘要不同的完整应用在同一安装路径替换，凭据直接读取且连接恢复，不再等系统授权；随后恢复正式构建。证据保留在0.49.9交付目录。每次构建直接复制 `native-keychain/EmployeeClientKeychain` 及清单所固定的内容，缺失时默认报错。`verify-stable-owner.py <app-path>` 可使用系统登录钥匙串中的无敏感测试条目验证两个不同签名调用方构建，并清除该测试条目。
